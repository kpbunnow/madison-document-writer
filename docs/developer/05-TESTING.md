# Verification and release process

From a fresh source copy, run:

    npm ci
    python3 -m pip install --require-hashes -r requirements-dev.txt
    npx playwright install chromium
    python3 tools/build.py
    python3 tools/verify_release.py

Playwright is pinned in package-lock.json. On an offline development machine, set `DW_BROWSER` to an independently installed compatible Chromium executable instead of downloading a browser. The runner launches the selected browser before any suite. A missing or unusable browser produces one message naming both setup options. A browser download failure is not a passing check; use the documented alternative only if a usable browser is actually available.

Build and test commands read app/, helper/, policy/, tests/, tools/ and docs/ directly. There is no flat copy of source and no source-map registration. Generated modules, runtime_identity.py, compiled policy, bundles, evidence and caches live under build/. Imports into helper and policy modules are resolved by the test runner's explicit PYTHONPATH. Test discovery reads tests/unit/ in place; production workflow suites remain in tests/browser/ and are invoked by the complete Chromium audit. Add files through normal imports, test discovery and the deployment manifest as appropriate. tests/README.md indexes every suite by feature; list a new suite there (a repository test enforces it). Browser workflow suites are added as one row of the browserSuites table in tests/browser/audit_browser.js. JavaScript suites call bundle functions by their top-level names, so a function does not need to be exported for a test; export only what another module imports (the four test-build hooks in app_core.js are the exception). JavaScript suites read the built page and its embedded bundle through tests/fixtures/built_bundle.cjs (builtPage, bundleSource); tests/fixtures/bundle_test.cjs also creates a standard DOM for short suites.

The gate includes ESLint on app/modules and shared.js, TypeScript contracts, Ruff pyflakes rules (F), Vulture at 60 percent confidence with individually justified framework whitelist entries, formatting, all retained suites plus R51 regressions, and fresh production Chromium, axe and PDF checks. Each regression suite has a 150-second deadline. tools/run_tests.py runs most suites in a small worker pool (DW_TEST_WORKERS overrides the default of up to four); suites that launch Chromium run one at a time afterwards, and the measured performance suites run last and alone. Browser workflow suites retain all assertions and have explicit individual deadlines. Do not relax deadlines or remove assertions to obtain a passing release.

**Fast development tier (reduced coverage, never release evidence).** While iterating on a branch you may run

    DW_FAST=1 python3 tools/verify_release.py

It runs the same formatting, static, regression and browser stages except that it skips the measured performance suites (audit_r48_performance.py, audit_r49_performance.py) and audit_case_projection.py compares one generated-corpus seed (2,000 cases, fast-only threshold of 1,500 comparisons) instead of three (threshold 5,000). Its evidence is labelled `"mode": "fast"` (regression evidence.json, browser-results.json) and it writes only build/verification/latest/fast-verification.json, never verification.json or repository.json. Every run first deletes the previous run's evidence, so an aborted or failed run never leaves earlier results in place. Packaging refuses fast or unlabelled evidence. The full gate (without DW_FAST) is mandatory before proposing any PR and before packaging.

**Test teardown and projection captures.** JavaScript suites whose completed work leaves only the application's long UI timers pending (15-second warnings and errors, 7-second progress, the Reports handoff notice) pass their completion to tests/fixtures/settle_ui_timers.cjs. After completion settles, ordinary pending work runs normally; then the remaining timers of a second or longer run one at a time instead of being waited for. Every callback still runs and its errors still fail the suite; production durations are unchanged. In the gate, tools/run_tests.py captures the seven Writer flows that audit_case_projection.py compares while they run in the pool (a fresh build/test-results/projection/ directory, each capture bound to the run, suite and source fingerprint and published atomically), and runs the projection check afterwards; a missing, failed, stale or malformed capture fails explicitly. Run on its own, audit_case_projection.py runs those flows itself.

**Feature suites and execution classes.** `audit_feature_*.js` suites group scenarios by feature. tests/fixtures/scenarios.cjs runs each scenario in its own child process, so every scenario keeps a fresh bundle, DOM, application state, storage, mocks and timers exactly as a separate suite would; the suite fails when any scenario throws, rejects, exits non-zero or prints nothing (audit_scenario_harness.js). Scenario labels start with the suite each came from, and tests/README.md maps former suite names (Consolidation Phase 6 moved R60–R62 suites, including audit_r62_import_rules.js, audit_r62_history_notes.js and audit_r61_development.js, into feature suites unchanged). Keep each feature suite under the 150-second per-suite deadline; split it when it approaches the limit. tools/suite_classes.py decides which suites may launch Chromium and therefore run one at a time: the suite text, or any local module it requires transitively, mentions chromium, playwright or DW_BROWSER (audit_suite_classes.py), so a browser launch moved into a shared helper keeps its suite serial.

The runner starts each suite in a separate process group and terminates its scenario descendants on timeout (tools/suite_process.py, audit_suite_process.py). A hung scenario cannot survive the unchanged 150-second suite deadline and overlap later suites. Windows cleanup uses taskkill /T /F; automated Linux checks do not establish native Windows acceptance.

**Production-only suites.** Unit suites run against a test build (`DW_TEST_BUILD=1 python3 tools/build.py`, which tools/run_tests.py makes in build/dist), but audit_contracts.js, audit_r50_documents.js, audit_r50_session_browser.js, audit_r54_extension_print.js and audit_r54_extensions.js compare the production bundle. They read `DW_PRODUCTION_DIR` (the full runner sets it to a copy of the production build) and otherwise build/dist. Each checks the bundle itself (tests/fixtures/built_bundle.cjs: a production bundle keeps the desktop-shortcut reconnect guard that test builds compile out and carries no test fixtures) and stops with: "This suite compares against the production build; run `python3 tools/build.py` without `DW_TEST_BUILD` first or set `DW_PRODUCTION_DIR`." To run one alone after a test build, build production into another directory and point `DW_PRODUCTION_DIR` at it. audit_r51_layout.py compares the shell with its script replaced, so either build works there.

**Current authoring expectations.** tests/fixtures/authoring_expectations.cjs pins, independently of application code, the authoring version each document family uses when created under the current release (initial notice, reinspection follow-up, all-item extension, scoped order). Use it only where an assertion means the current format for that family; keep literal versions where a test means a specific historical format. It refuses to load when version.json's authoring version differs, so an authoring change updates that one reviewed table.

Print checks compare 69 authored document variants, the frozen stylesheet and all four court copies exactly against the retained verified R49 runtime. Pagination checks require page bounds, no overflow or clipped content, complete continuation headers and preserved authored content. Authoring-9 snow covers are tested with controlled font metrics producing one and two cover pages; their rendering is unchanged. Native City printing including an R33-era snow citation remains an open acceptance item.

The R51 shell parity test follows the explicitly listed substitution model described in `docs/history/R51-REVIEW.md`. For an intentional screen CSS correction, document the exact difference and require that exact replacement once in each affected shell before reversing it for comparison with the unchanged historical hash. Do not regenerate the reference hash or strip arbitrary CSS. The current reviewed exceptions are: (1) removing only the shared button background transition so text and background switch themes together; the border transition remains; (2) the R56 usability phase 3 screen-only block appended to the end of app/assets/ui-refresh.css, beginning with the comment `/* R56 usability phase 3 (screen only):`. It styles the Review all items / One item at a time control, its step indicator and collapsed tips, the collapsed Administrator tools group, the narrow-screen (760px and below) compact editor header with its single fixed task bar, which hides while a field is focused or a dialog is open and is never printed, and the 320px reflow rules: at 860px and below an editable due-date cell wraps its selection box, date and remove button inside the item card and long header values wrap; at 420px and below header labels sit above their fields; at 760px and below the Document actions menu opens aligned to the right edge of the action row. (3) The R59 screen-only block is appended directly after the phase 3 block and begins with the comment `/* R59 screen styles (screen only):`. It defines the type tokens (titles, section and subsection headings, body, labels, tables, buttons, hints and errors, badges and chips) and applies them to every Writer screen and the Reports chrome but never to the document sheet or print; above 860px it keeps an editable due date inside its cell so the remove button never covers its calendar button, and shows the remove button while its row has keyboard focus; and it styles the selected inspection candidate, the issued case row in Workspace (with an outline in forced colors) and the Review dialog sections. audit_r51_layout pins the exact size and SHA-256 of each of the phase 3 and R59 blocks, requires each exactly once in each built shell and removes both before comparing with the unchanged historical hash. Missing or altered correction bytes and unrelated shell changes still fail. The approved print stylesheet and historical PDF fixtures remain frozen and are checked separately by the production browser audit. Application code has no whole-bundle hash to update; code changes are checked through their rendered output, print and court-copy parity and the regression suites.

Browser audits bring the page being inspected to the foreground. On system Chromium 154, a ten-click/fill diagnostic took about 15.2 seconds after another tab opened, versus 0.36 seconds after `bringToFront()`. Foreground the Writer again after Reports and restoration-profile work; keep measured browser suites serial and retain their existing deadlines.

Fingerprints bind evidence to maintained source and production output before and after verification. Archive material, dependencies, generated evidence and caches are excluded from maintained source. Packaging refuses a changed tree, missing suites or changed browser hashes. Releases have no signing key; do not introduce one or alter release trust.

After a passing gate, package to a new folder outside the source tree:

    python3 tools/package_release.py --output ../release --published-manifest /path/to/last-approved-deploy/runtime-manifest.json

Release packaging: tools/package_release.py writes runtime-manifest.json for every deployed file through tools/deploy_manifest.py, then rechecks the finished deploy folder with helper/verified_update.py. audit_r50_updates.py, audit_r51_updates.py, audit_r51_bootstrap.py, audit_r50_connections.py and audit_r52_manifest.py cover the manifest, tamper classes, downgrade protection and the launcher hand-off.

Automated axe does not establish WCAG conformance. City Windows, ACL/SMB/SQL, Outlook, native printing, staff tasks, legal and seasonal decisions remain in ACCEPTANCE-RECORD.md. Never mark those items accepted from automated checks.

## Source ownership and deployment evidence

`tools/source-inventory.json` lists every maintained source-package file. Review and stage additions/deletions, then run `python3 tools/release_inputs.py --update-source-inventory` and review/stage the inventory diff. Unexpected maintained files refuse packaging; local credentials, environments, operational folders and caches are excluded before reading and cannot be registered. Links/reparse points in owned inputs are refused. This inventory also works in extracted source ZIPs without Git; root SHA256SUMS.txt is generated archive metadata, not maintained input. Uncommitted content changes still require fresh exact-byte verification and reviewed checkpoints.

The gate fingerprints all mapped deployment inputs, vendored runtime bytes and generated release records. Packaging checks them before output, after copy and before archives, retaining the installer manifest verifier. `audit_release_inputs.py` exercises the real packager with isolated synthetic inputs, including altered generated policy/identity/guidance and private files.

The manual Markdown is authoritative. Before verification, run `python3 tools/build_manual.py` with pandoc, pdftotext and the pinned Playwright browser available to regenerate HTML, Word and PDF. It renders all three in a staging folder under docs/staff, validates them and replaces them together under a journal; a failure or interruption leaves the previous editions. Each edition carries a digest of PROGRAM-MANUAL.md and manual-style.css. The 22 chapter anchors and original screen/print style are retained. Manual editions are committed inputs; the gate never regenerates them, but audit_r55_documentation fails when any edition does not match the current sources. pdftotext (poppler-utils) is a required gate prerequisite: PDF inspection fails rather than skips without it.

R60 appends one screen-only block after the unchanged R59 block in ui-refresh.css. It compacts the Workspace entry panel to retain the first case action above the desktop fold, lays four navigation items into a two-by-two narrow-screen grid, and flows the document editor’s mailing address beneath its expanding header on desktop widths, reduces the residual window spacer and hides the obsolete fixed-position screen window label. It is scoped to .document-workspace and never enters printableHTML’s approved stylesheet. audit_r51_layout pins its exact bytes and removes only this explicit block, plus the existing reviewed exceptions, before comparing the unchanged historical shell hash. The R59 block boundary now ends at the R60 marker; all prior hashes remain unchanged. audit_r60_development and browser_r60 cover the new decisions and real dialog/address/PDF behavior.

R62 adds audit_r62_import_rules.js, audit_r62_extensions.js, audit_r62_extensions_helper.py, audit_r62_history_notes.js and browser_r62.js for import eligibility, authoring-16 extensions and helper parity, history notes and referred-case options. R61 adds audit_r61_development.js and audit_r61_best_interest.py for authoring-15 histories/compliance, explicit Best Interest safety confirmation, currency units, legacy classification aliases and complete citation packets. browser_r61 covers new history PDFs and signer-free Best Interest output; browser_r26 publishes the simplified Best Interest through the real helper with obsolete review fields absent. browser_r33 checks mocked-delivery byte binding and real Chromium packet content, then browser_r61 files selected regular/snow/corrected-snow packets through actual HTTP receipts and checks original bytes plus identical repeat retrieval. Its helper renderer is the documented test-only fixture loaded with actual Chromium PDF bytes; native Windows/Outlook handoff is not established. Historical authored-print hashes and the approved stylesheet remain unchanged.

The runner's read-only `python3 tools/run_tests.py --check-browser-only` diagnostic checks browser availability without touching evidence. Every actual regression run invalidates its previous regression/print evidence before the precheck, including when the browser is unavailable. Nested diagnostics use the read-only command so they cannot delete their parent gate's evidence.

The [development standard](DEVELOPMENT-STANDARD.md) defines PR formats, required CI checks and publication inputs. Packaging requires the last approved deployment manifest (or an explicit genuinely first-publication declaration). Source/version validation and immutable publication checks run without changing installer trust. The gate records reviewed Git provenance when available, a verified-input digest and actual toolchain; source ZIPs remain verifiable without Git.

Feature-owned event registration is covered by audit_event_registration.js and tests/fixtures/feature_event_order.json (original core registration order, capture flags and state/startup checkpoints). Preserve synchronous action dispatch and first-match routing. Do not replace the per-target registration guard with repeated render-time registration. MODULE-CLEANUP.md lists feature owners and the remaining cleanup increments.

`audit_record_rules.js` loads the record APIs without Writer startup, disables ambient clock/randomness while exercising them, and checks deterministic legacy IDs, retained authoring/frozen sources, correction replay, carry-forward, shape/history/merge refusals and explicit projection facts. `audit_case_projection.py` still compares the actual summarize adapter against the independent helper across every full-mode seed and captured Writer flow. Shape validation never substitutes for integrity verification.

`audit_writer_services.js` checks the six scoped feature interfaces, lazy construction, unchanged initialization/listener order and loading without Writer startup. Its navigation scenarios exercise readiness, failed saves, superseded navigation and edits made during a pending save; citation scenarios retain pending/issued guards and deposit requests. `audit_module_boundaries.js` caps the remaining Writer cycle at 15 and Reports at 5 and prevents these owners from importing back into UI orchestration. Factories still install their original listeners; only the separate event-registration service promises per-target duplicate protection.

`audit_writer_feature_boundaries.js` covers the administrator, address, new-document and test-only fixture factories without Writer startup. It retains exact named lazy interfaces/initialization order, original click registrations and test-build gating, and checks explicit address acceptance/stale-result refusal, administrator receipt bindings, historical extension selection and live visit replacement. The boundary allowlists exclude UI orchestration imports and retain the 15/5 Writer/Reports cycle caps.
